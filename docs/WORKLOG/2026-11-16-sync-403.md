# Fix GitHub Sync 403 (merge-upstream) — 2026-11-16 (updated)

## Audit (dashboard → GitHub API)
- **Flow:** Dashboard (`DASHBOARD/app.js`) POST `/api/sync` `{dry_run:false, confirmation:"SYNC", repositories:[...]}` → `api/routes.py` resolves token (Bearer header or server-side session token from `/api/auth/*`), builds `GitHubClient(token)` and `ForkSynchronizer`, validates selection, **rechecks status server-side**, and merges only repos currently `behind`; diverged never auto-synced.
- **Request:** `GitHubClient.merge_upstream` (`fork_sync/github.py`) → `POST https://api.github.com/repos/{owner}/{repo}/merge-upstream` with `Authorization: Bearer <token>`, `Accept: application/vnd.github+json`, `X-GitHub-Api-Version: 2022-11-28`, JSON body `{"branch": "<branch>"}` via `_request`.
- **Error diagnostics:** `ForkSynchronizer._github_error_details` surfaces HTTP status, GitHub `message`, `errors`, `documentation_url` (or body snippet) in sync results (preserves actual response content). No tokens/secrets logged.

## Confirmed root cause (code defect) — FIXED
- **Defect:** `sync_fork` passed `upstream_branch` (parent/upstream default branch name) to `merge-upstream`. Per GitHub merge-upstream semantics the `branch` field specifies the branch in the fork to update (the fork’s branch receiving upstream changes). This was incorrect when fork default branch name differed from upstream’s, and is not the intended/correct request construction.
- **Fix (minimal):** `fork_sync/synchronizer.py` now passes `fork_branch` to `merge_upstream` (`self.github.merge_upstream(full_name, fork_branch)`). Regression test updated: `tests/test_synchronizer.py::test_sync_fork_when_behind_upstream_targets_fork_default_branch` (expects merge called with fork branch `master` while compare still uses upstream `main`).

## Not a confirmed code defect (but required for 403 resolution)
- Auth header/type, endpoint/method, token source (session/bearer, per-request client), server-side recheck/safety, and error-body surfacing are correct per audit/tests.
- **HTTP 403 from merge-upstream with working preview/read** is consistent with GitHub-side authorization/permission issues: GitHub App repository permission must include **Contents: Read and write** (and Metadata read), the app installation must grant access to the specific fork repositories/account, and the authenticated user must have write/push access to the fork; token must carry required grants. **Actual 403 cause cannot be confirmed without captured live response body from the running updated app.**

## Live result (confirmed)
- **Real Sync:** successful after installing/granting the GitHub App in the same profile/account context as the target fork and providing repo access.
- **Confirmed 403 root cause:** GitHub App installation/repository access was not covering the relevant profile/fork (not a code defect in merge-upstream request/auth construction).
- **36 vs 1 processed:** UI sends only selected `behind` repos and reports `Sync: <returned results> processed` (= requested/returned count), not total repos; no backend defect confirmed.
